# Revue adversariale — code par SMS de secours et avis croisés (two-factor-auth 2.35.0)

Date : 18 novembre 2026. Revue indépendante, en lecture seule, du commit `bd1521491` (greffon, 2.34.2 → 2.35.0) et du
commit `6b8a82f` de `admin-console`. Référentiel : OWASP ASVS niveau 2 (V2 Authentification, V3 Sessions).
Aucune requête vers la production ni l'annuaire, aucun SMS ni courriel. Essais jetables sous
`/root/.claude/jobs/058512ca/tmp/revue-2fa-sms/` (supprimés).

Légende : **prouvé** = essai exécuté, résultat cité ; **plausible** = déduit du code, non rejoué ; **à vérifier** = dépend
d'une configuration de production que cette revue n'avait pas le droit de lire.

## Verdict court

Le cœur tient : un code SMS ne peut ni servir de preuve en session (`reauth` exclu, `p`/`c` séparés), ni ouvrir
l'inscription d'un autre facteur, ni être pris pour un code courriel ; le numéro ne vient jamais du navigateur ; les
réponses de l'écran de connexion sont uniformes et rien n'est écrit pour une adresse inconnue ; tous les écrivains de
`etat/<sha256>.json` conservent la clé `mobile`. Les défauts trouvés sont des **bords** : le SMS n'est pas lié au numéro
enrôlé, « jamais seul » compte des drapeaux plutôt que des facteurs utilisables, la publication des mobiles peut perdre
ou écraser de l'état, et le déni de service du secours est possible. Aucun contournement direct du mot de passe ou d'un
facteur fort par un anonyme n'a été trouvé.

## Détail

### 1. Pas de liaison au numéro enrôlé — moyenne, prouvé

`index.php:1909-1943` (`DoSmsCodeEnable`) ne mémorise **rien** du numéro : `SmsOn = true` seulement. À chaque demande, la
console relit le mobile **courant** (`bin/console` branche SMS, `fnMobileC`). Le code d'enrôlement « prouve que ce numéro
répond » (commentaire de `DoSmsCodeEnable`), mais cette preuve est perdue dès que la fiche change.

Scénario : Sana enrôle +216 20 123 945. L'opérateur recycle le numéro, ou la console (inscription, import d'organisation —
`UserProvisioner.php:713`, `Organisation.php`) réécrit `mobile`. `sms:mobiles` republie le masque ; les codes de connexion
partent maintenant au nouveau titulaire. Le seul signal est l'avis courriel « quelqu'un a demandé un code » (envoyé
seulement s'il y a une demande). Un administrateur d'organisation qui provisionne ses membres peut donc rediriger leur
secours, ce que la formulation « numéro de l'annuaire vérifié à l'inscription » ne couvre pas.
Le webmail ne peut pas, lui, changer `mobile` : l'ACL du nouvel annuaire (`deploy/ldap/20-annuaire-sky.ldif`, règle {3}
`to * by self read`) refuse l'écriture à la personne. **À vérifier en production** avec `deploy/ldap/verifier-acl.sh` ;
l'ancien arbre `dc=convergent,dc=tn` a, lui, `to * by self write` (`10-skyconsole-acl.ldif:46`), donc `mobile` y est
modifiable avec le seul mot de passe, ce qui ouvrirait un contournement complet du TOTP si cet arbre sert l'authentification de smail.

Preuve (`R2`) : après enrôlement avec le masque `…945`, l'état publie `…111` ; `DoSmsCodeLoginRequest` met toujours un
code en file et `DoGetTwoFactorInfo` rend `SmsMasked = '+216 •• ••• 111'`, `SmsOn = true`.

Correctif : la console publie, avec le masque, une empreinte **à clé** du numéro entier (`HMAC(clé partagée, E.164)`, pas
le numéro) ; l'enrôlement la mémorise (`SmsNum`) ; émission et connexion comparent et, si elle diffère, éteignent
`SmsOn` et ne rien envoyer ; avis par l'autre canal au changement. Au minimum : avis courriel à chaque republication d'un
mobile différent pour un compte qui a `SmsOn` (ce que `sms:mobiles` peut faire, il voit l'ancien masque).

### 2. `sms:mobiles` et la limite de taille LDAP — moyenne, plausible

`SkyDirectory::mobiles()` (`src/Api/SkyDirectory.php:332-363`) fixe une limite **cliente** de 100 000 mais n'examine
jamais `ldap_errno()` après un résultat obtenu. Un serveur OpenLDAP sans `olcSizeLimit` (aucun dans `deploy/ldap/`) coupe
à **500** par défaut pour une identité non privilégiée ; PHP rend alors un résultat partiel avec l'erreur 4, que `@`
masque. La commande (`bin/console:3846-3899`) conclut « l'annuaire a répondu, donc leur absence est un fait » et met
`mobile: null` pour tous les comptes au-delà de la coupure. Même défaut dans `comptesPlus()` (l'échéance des comptes plus).
Aujourd'hui smail.tn est petit ; le défaut apparaît à la croissance, sans message.
Correctif : refuser (`null`) si `ldap_errno($rConn)` vaut 4 (ou toute erreur non nulle), ou paginer (`ldap_control_paged_result`) ;
nommer l'identité LDAP et sa limite dans `docs/GUIDE-ADMIN.md`.

Sûreté du filtre : `(&(objectClass=inetOrgPerson)(mobile=*))` est constant ; le domaine, seule donnée variable, passe par
`^[a-z0-9-]+(\.[a-z0-9-]+)+$` avant d'entrer dans le DN : aucune injection. Base `ou=People,dc=…,<domainsDn>` : bornée.
Une base absente (code 32, faute de frappe dans `signup.domain`) rend `array()` et **retire tous les mobiles** (même
famille que ci-dessus).

### 3. Écrasement de `etat/<sha256>.json` — moyenne, prouvé

`CodeConnexion::publierMobile()` (`src/Consumer/CodeConnexion.php:190-210`) lit le fichier, puis `is_array(...) ? … : array()`.
Un fichier **illisible ou tronqué** devient un tableau vide : la réécriture ne contient que `mobile`.
Or `Passage.php:161` écrit l'état **sans** fichier temporaire ni verrou (`@file_put_contents($sFichierF, …)`), si bien
qu'un lecteur voit un fichier à moitié écrit. Preuve (script jetable) : fichier d'état tronqué à 40 octets
(formule, `secours` vérifié, `avoir_millimes`) → `publierMobile` rend `true` et le fichier devient
`{"mobile":{"present":true,"masque":"+216 •• ••• 945"}}` : l'adresse de secours vérifiée, l'avoir et le reste sont perdus.
Même motif dans `Secours::versEtat` (`Secours.php:99-111`, lecture identique), non nouveau mais désormais exercé en rafale
par `sms:mobiles`. De plus `Secours.php:110`, `CodeConnexion.php`, `bin/console:3892,4156,4187` écrivent dans le **même**
`<fichier>.tmp` : deux processus simultanés s'écrasent, et un `rename` peut publier le contenu de l'autre.
Conséquence concrète : un compte perd son adresse de secours vérifiée (`secours.verifiee`) → plus de code courriel ;
état de paiement perdu.
Fenêtre étroite (millisecondes) mais réelle ; `sms:mobiles` n'écrit que si le masque change, ce qui la réduit.
Correctif : dans `publierMobile` et `versEtat`, si le fichier existe et n'est pas un objet JSON valide, **ne rien écrire**
(`return false`) ; un nom temporaire aléatoire (`.tmp.<hex>` comme `Decision.php:497`) ; un `flock` commun
(`<fichier>.verrou`, comme `Parrainage.php:245`) pour tout lire-modifier-écrire de ce fichier ; `Passage.php:161` en
temporaire + `rename`.

**Écrivains de `etat/<sha256>.json` relus (conservent tous `mobile`)** : `Passage.php:149-161` (fusionne sur le contenu lu),
`Passage.php:243-250` (idem, `LOCK_EX`), `Decision.php:313-333` `poserAvoir`, `Decision.php:493-505` `poserEtat`,
`bin/console:1872-1887` `fnPoserEtatP2` (appelants : `array_merge($fnEtatP2(...), …)`, `Parrainage::prolonger` rend l'état
entier), `bin/console:4156-4165` (masques), `bin/console:4187-4195` (alias), `Secours::versEtat`, `CodeConnexion::publierMobile`,
`bin/console:3885-3896` (retrait). Aucun ne reconstruit le fichier de zéro ; aucun autre trouvé par `grep` sur
`fichierEtat` et `etat/`. Le risque n'est donc pas l'omission de la clé mais la concurrence (ci-dessus).

### 4. « Jamais seul » compte les drapeaux — moyenne à faible, prouvé

`TwoFactorRecord::hasFactor()` (`providers/record.php`) tient `EmailOn` pour un facteur ; `smsActive`, `dropSmsAlone` et
`issueEmailCode` s'y fient. Mais `EmailOn` ne dit pas que le courriel **peut** servir : il faut une adresse de secours
vérifiée hors domaine (`recoveryAddress`) et un domaine qui ne l'a pas éteint (`emailCodeDomainAllowed`).
Scénarios : (a) Lina a `EmailOn` + `SmsOn`, puis change d'adresse de secours (non vérifiée tant qu'elle ne confirme pas) ou
la retire ; (b) l'organisation pose `code_secours: false` (politique 2.34.0). Dans les deux cas le courriel ne répond
plus et le SMS est **le seul** facteur utilisable avec le mot de passe. Preuve (`R3`) : enregistrement `EmailOn`+`SmsOn`,
sans adresse de secours : `DoSmsCodeLoginRequest` met un code en file, ce code ouvre la connexion
(`directory+ok`), alors que `DoEmailCodeLoginRequest` n'envoie rien.
Le TODO (§12) reconnaît l'absence de politique de domaine pour le SMS ; c'est ici plus grave : une organisation qui a
interdit les facteurs « personnels » garde un SMS actif.
Correctif : à l'émission (et au jugement), exiger un facteur **utilisable** : TOTP actif, clé lisible, ou `EmailOn` avec
`recoveryAddress != ''` et domaine autorisé ; et une politique `code_sms` par domaine à côté de `code_secours`
(`etat/domaines/…`), échouant fermé comme elle.

### 5. Déni de service et coût — faible à moyenne, prouvé

Plafonds : par compte 3 codes/15 min et 10/jour **par canal** (`SmsSends` distinct de `EmailSends`) ; par IP 10 requêtes/h
**au total** (`ipAllows`, courriel et SMS confondus, comptées même pour une adresse sans facteur) ; console : 6 codes SMS/15 min
par compte (inatteignable depuis le greffon, utile seulement si `codes/` était forgé), un avis par compte et par canal toutes
les 15 min. SMS maximal par compte et par jour : 10 codes + 10 avis (chaque code courriel envoyé déclenche un avis SMS)
= **20**, déclenchables par un anonyme sans rien savoir d'autre que l'adresse, à condition que le compte ait `SmsOn` (codes)
ou un mobile publié avec `EmailOn` (avis).
Par heure et au total : `min(10 × nb_IP, 12 × nb_comptes_éligibles)` ; une IPv6 est comptée par /64, donc un /48 donne 65 536
« adresses ». Le seul plafond global est `Budget` — **seulement si `plafond_heure` est posé** : `Configuration.php:92-95`
renvoie l'envoyeur nu sinon. Il est **partagé** avec l'inscription et « mot de passe oublié » : une inondation de codes
les affame (`indisponible`).
Preuve du déni du secours (`R4`) : un navigateur « attaquant » demande 3 codes pour le compte de Lina (trois IP) ; le
navigateur du titulaire, depuis une autre IP, voit sa demande **refusée sans message** : 3 codes en file au total (tous liés au
navigateur de l'attaquant), aucun lié au titulaire. Pour un utilisateur dont le seul recours est le SMS, le secours
est indisponible jusqu'à 24 h glissantes avec **10 requêtes par jour**.
Correctifs : plafond par (compte, navigateur) en plus du plafond par compte, et message qui distingue « limite atteinte »
sans révéler l'existence du compte (réponse uniforme, mais le secours du titulaire doit survivre : compteur séparé pour les
demandes provenant d'une session déjà passée par le mot de passe n'est pas possible avant le mot de passe — accepter donc un
plafond plus généreux, 5/15 min, ou la lutte par `fail2ban` sur l'IP) ; compteur `Budget` **par motif** (`connexion` ≤ 20 %
du plafond) ; refuser le démarrage de la console si `plafond_heure` est absent.

### 6. Pas de comptage des essais avant le mot de passe — faible, prouvé

`CheckBeforePassword` juge sans écrire (`index.php:518-545`, choix documenté pour qu'un anonyme ne verrouille pas le
titulaire). Donc le compteur `n` des codes (`EMAIL_TRIES = 5`) n'avance jamais dans le parcours de connexion, car un mauvais
code lève `AuthError` avant `DoLogin`. Preuve (`R1`) : 60 mauvais codes à 8 chiffres avant le mot de passe → `n = 0`,
`Failures` vide, compte non verrouillé, et le bon code passe ensuite (`directory+ok`). Espace : 10^8, jusqu'à 3 codes SMS
(+3 courriel) vivants 10 min : environ 6·10⁻⁸ par essai ; il faut ~170 000 essais pour 1 %, soit 550 req/s tenant 3 s chacune
(`precheck_delay`), seulement limité par IP/fail2ban. Le gain est borné (il faut encore le mot de passe) et l'attaquant
doit avoir fait envoyer un SMS au titulaire, mais le point 6 de l'analyse (« 5 essais ») est faux avant le mot de passe.
Correctif : corriger le TODO ; compter les échecs **par code vivant et par navigateur** au prix d'une écriture (bornée : le
code n'existe que si un SMS a été demandé, donc le titulaire ne perd rien qu'il n'ait déjà perdu), ou raccourcir la
validité SMS à 5 min.

### 7. Le bouton est offert partout, même sans mobile publié — faible, plausible

`FilterAppData` (`index.php:~217`) publie `TwoFactorSmsLogin = smsOffered()` pour tout visiteur, qui ne dépend que de
`email_code_dir` et de `sms_code`. Tant que `sms:mobiles` n'a pas tourné (aucune unité planifiée : `grep sms:mobiles deploy/`
rien, `TODO.md` console l.24 « à planifier »), personne n'a de `mobile` dans `etat/` : la demande rend la phrase habituelle
et **rien ne part**. Un titulaire qui a perdu son TOTP attend un SMS qui ne viendra pas. Correctif : planifier avant
d'activer, ou activer `sms_code` seulement quand la console a publié (fichier `etat/mobiles.json` avec la date du dernier
passage). Un titulaire créé après le dernier passage attend aussi, jusqu'au suivant : prévoir un déclenchement à la création.

### 8. `codes-debit/` et l'IP — faible, plausible

`ipAllows` crée un fichier par IP (ou /64) dans `codes-debit/`, sans purge, jamais lu après une heure : croissance
illimitée pour un attaquant IPv6 (inodes). Et `GetClientIp(http_client_ip_check_proxy=false)` derrière un mandataire
rendrait l'adresse du mandataire pour tous (10/h pour tout le monde, déni complet) : **à vérifier** sur smail.tn (le banc
fixe l'IP, `Actions::$ip`). Correctif : purge des fichiers de plus d'une heure dans `ipAllows` (1 fois sur 50) ou par la console.

### 9. Pannes : annuaire muet, envoi raté, sans `state_dir` — faible

* Envoi raté : le code part en file, aucun avis (`echec`), l'écran répond « envoyé » ; correct et voulu.
* Annuaire muet : `fnMobileC` attrape tout et rend `''` → audit `sans_mobile`, indistinguable de « pas de mobile » : on perd le
  signal de panne, et l'avis par SMS d'un code courriel est perdu en silence. Distinguer `annuaire_muet`.
* Sans `state_dir` : `permis()` échoue fermé (`mkdir('')`), **aussi pour le code SMS** (`code-sms`), qui devient `plafond` :
  aucun SMS ne part et le journal parle de plafond. Échec fermé, bon ; nom trompeur.
* Avis courriel : destinataire = adresse de secours **vérifiée** de l'annuaire (`$oApp->secours()->verifiee`) hors du domaine
  du compte, sinon l'adresse du compte (qu'un attaquant qui a le mot de passe lit) ; jamais l'adresse de la demande. Le
  texte ne contient ni code ni numéro. Bon.

### 10. Remarques

* Le TODO annonce « plafonds partagés avec le courriel » : le compteur par compte ne l'est pas (3+3 par quart d'heure).
* `DoSmsCodeRequest` (enrôlement) ne demande pas de preuve pour **envoyer** : une session volée fait partir 3 SMS/15 min vers
  le titulaire (la preuve est exigée à l'activation).
* Rien ne distingue une session ouverte par SMS d'une autre (pas de marque) ; elle ne peut pourtant ni changer l'adresse de
  secours, ni désactiver, ni ajouter un facteur (preuve exigée, SMS refusé en `reauth`).
* La ligne de journal du greffon contient l'adresse tapée (résolue par le cœur) : aucun code ni numéro, conforme.
* Le masque (`+216 •• ••• 945`) livre trois chiffres à la session : négligeable ; il est revalidé (`/^\+?[0-9 •*]{4,32}$/Du`).

## Ce qui tient (vérifié)

* **Le SMS n'est jamais seul au sens des drapeaux** : `smsActive` exige `hasFactor` ; `dropSmsAlone` à la lecture et à
  l'écriture (`saveRecord` est le seul `Put`, `index.php:2163`) ; boîte WebAuthn illisible = pas de suppression sur un
  doute mais `smsActive` faux (échec fermé) ; retrait du dernier facteur (TOTP, clé, courriel) efface `SmsOn` (essais
  existants) ; la course entre deux requêtes est fermée par le verrou par compte (`underLock`) et la relecture sous verrou
  dans `DoSmsCodeEnable`.
* **Un SMS n'affaiblit rien** : `proveWith` → contexte `reauth` sans `c`, donc canal courriel seul ; `issueEmailCode` refuse
  `reauth` en SMS ; `guardRecoveryChange` passe par `proveWith`. Activation = facteur courant **et** code ; désactivation =
  facteur courant. Un code SMS d'`enroll` ne sert pas en `login` (`p` comparé) ; un code `login` ne sert pas à l'activation.
* **Courriel et SMS ne se confondent pas** : listes (`SmsCodes`/`EmailCodes`) et préfixes de hachage séparés ; à la connexion
  (`c = both`) chaque canal compte ses essais sur sa propre liste.
* **Énumération** : réponse constante (`jsonResponse(..., $bOffered)`), attente 1,0–1,3 s pour tous les chemins
  (`ip-limit`, `error`, `none`), rien d'écrit sans `etat/…mobile` **et** `SmsOn` (aucun répertoire de stockage créé pour une
  adresse quelconque : le verrou n'est atteint que si `smsMasked` est non vide), mêmes lignes de journal interne.
* **Rejeu, liaison, expiration** : usage unique, lié au jeton de connexion (le code d'un autre navigateur est refusé), 10 min,
  `hash_equals`, jamais de code dans le journal du greffon ni l'audit de la console.
* **Le numéro** ne vient jamais de la demande : `codes/*.json` ne porte que adresse, code, langue, canal (`canal` inconnu
  → demande écartée, `Secours::demandeCode`) ; la console relit `ldap_read` sur un DN construit par une liste blanche
  (`personDn`, `InvalidArgumentException` sinon) ; domaine servi seulement.
* **Avis** : jamais à une adresse fournie par la demande, sans code ni numéro, un par compte et par canal par quart d'heure,
  sous verrou, échoue fermé, seulement après un envoi réussi.
* **Le greffon n'a jamais le numéro entier** : seulement le masque publié.

2. Corriger `mobiles()` (taille, erreur 4) et `publierMobile`/`versEtat` (fichier illisible, `.tmp` unique, verrou) (2, 3).
3. Compter les facteurs **utilisables**, et une politique `code_sms` de domaine (4).
4. Exiger `plafond_heure`, séparer le budget par motif, plafonner par navigateur, purger `codes-debit` (5, 8).
5. Planifier `sms:mobiles` (minuteur et à la création de compte) **avant** d'activer `sms_code` (7).
6. Corriger le TODO (essais, plafonds partagés) ; séparer `annuaire_muet` de `sans_mobile` (6, 9, 10).
